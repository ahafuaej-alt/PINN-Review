## 4. Scientific-authority boundary after freeze

The freeze establishes the following hierarchy:

- **Scientific meaning:** locked Drive `v0.7-pilot-atlas-prefreeze` and its five single-owner documents remain authoritative.
- **Scientific workflow/QA:** locked v0.7 extraction/evidence protocol and QA remain controlling within their scopes.
- **Implementation planning:** Master Plan v1.0 controls the ordered architecture/implementation program.
- **GitHub implementation artifacts:** future schemas, ERDs, code, APIs, pages, migrations, tests and generated views must implement the frozen contract without redefining scientific meaning.
- **Master Memory:** records decisions, context and synchronized completion history; it is not a sixth ontology owner.
- **Computational Resources:** remains an independently governed bounded subsystem until a separately authorized stable integration checkpoint.

If implementation convenience conflicts with locked scientific meaning, scientific meaning prevails and the implementation must change.

## 5. Complete Atlas production-surface safeguard

Master Plan v1.0 freezes the rule that the current 26-route register is a **current-surface preservation/migration baseline only**.

It is not:

- the final menu;
- the final target information architecture;
- a maximum number of routes/pages;
- permission to preserve duplicated scientific authority indefinitely.

Task 9 remains mandatory before production migration/cutover and must discover additional production surfaces existing at audit time.

For every current/discovered surface, Task 9 must determine implementation/data dependencies, identifiers, read/write paths, authoritative owners, duplication, cross-links, deep-link stability, mobile/accessibility implications, migration impact, regression requirements and explicit future disposition.

Current routes may later be retained, redesigned, merged, nested, renamed, replaced, redirected or retired only after governed dependency/migration/regression treatment.

## 6. Future-page safeguard

The permanent architecture must support governed addition of future Atlas pages and page families without redesigning the entire ontology, database, navigation model or site for each addition.

Future pages must declare their purpose, authoritative upstream owners, paper-level versus synthesis scope, identifiers, read/write behavior, provenance requirements, taxonomy/relationship dependencies, update behavior, navigation/cross-links, QA/regression obligations and lifecycle policy where applicable.

A new page never becomes scientific authority merely because it exists.
